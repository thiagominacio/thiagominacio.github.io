Sistema de Gestão de Garantias

Da organização manual de solicitações ao desenho de uma aplicação centralizada para gerenciar clientes, atendimentos e o ciclo de vida das garantias.

Next.jsTypeScriptTailwind CSS PostgreSQLPrisma ORMDocker
Estágio atual: protótipo inicial, não implantado

Há uma base de aplicação e ambiente de banco de dados em desenvolvimento. Fluxos de atendimento, emissão de OS e integração com cliente ainda precisam de implementação e validação.

01 · CONTEXTO

O problema: informação espalhada e acompanhamento manual.

O projeto nasceu da observação de um fluxo de garantias: o cliente registrava sua solicitação em um formulário, os dados chegavam a uma planilha e uma segunda planilha era usada para acompanhar o andamento, as datas e a responsabilidade pelo atendimento. Esses controles também serviam de base para indicadores.

Embora atendesse à operação, essa estrutura tornava o histórico fragmentado e exigia conciliações e atualizações em lugares diferentes. Havia ainda a necessidade de gerar uma ordem de serviço (OS) e compartilhá-la com o cliente — funcionalidade não disponível naquele fluxo.

Objetivo: estudar e prototipar uma aplicação única, com dados estruturados e um ciclo rastreável de solicitações, para reduzir controles paralelos e preparar futuras automações.
02 · O QUE FOI DESENVOLVIDO

Uma fundação técnica para um sistema maior.

Foi iniciado um protótipo web independente, estruturado em Next.js com TypeScript, utilizando PostgreSQL em ambiente Docker e Prisma ORM para modelagem e acesso ao banco. Houve trabalho inicial de configuração do projeto e estruturação do cadastro de clientes.

✓
Iniciado e estruturado

Projeto web independente, com tecnologias do stack definidas e ambiente local configurado.

✓
Base de persistência

PostgreSQL e Prisma, com etapa inicial de modelagem de dados de clientes e migração do banco.

◷
Fluxo completo de garantias

Solicitações, estados, responsáveis, histórico, anexos e atendimento integrados permanecem como escopo a implementar e testar.

◷
Ordens de serviço e comunicação

Geração de OS, notificações e acompanhamento pelo cliente são funcionalidades desejadas para etapas posteriores.

A lista distingue avanços conhecidos do protótipo e escopo planejado. Não representa um software completo ou implantado em ambiente produtivo.

04 · REQUISITOS E TECNOLOGIA

Do levantamento do processo à arquitetura do protótipo.

O ponto de partida foi separar o que já existia — entrada de dados, controles em planilhas e indicadores — do que a solução deveria acrescentar. A arquitetura escolhida permite evoluir gradualmente para uma interface web com persistência relacional e regras de negócio próprias.

Competências que o trabalho evidencia

  • Levantamento de requisitos e identificação de gargalos operacionais.
  • Desenho de processos e definição de estados para atendimento de solicitações.
  • Planejamento de entidades e relacionamentos em banco de dados.
  • Configuração e desenvolvimento inicial de aplicação com stack web moderna.
  • Visão de integração entre dados de entrada, acompanhamento e indicadores.
  • Separação entre protótipo técnico, funcionalidades planejadas e implantação real.
05 · PRÓXIMAS ETAPAS

O que será necessário para virar um sistema utilizável.

1
Cadastros e entidades

Revisar regras de clientes, solicitações, ocorrências e atendimentos, com dados exclusivamente fictícios.

2
Fluxo de chamados

Implementar abertura, triagem, atualização de status, responsáveis e histórico.

3
Ordens de serviço

Desenvolver geração de OS e validar a comunicação do andamento.

4
Testes e qualidade

Validar permissões, integridade dos dados, tratamento de erros e jornadas completas antes de qualquer uso real.

06 · APRENDIZADOS

Por que este case é relevante para tecnologia.

Ele evidencia uma competência importante para funções de desenvolvimento de sistemas, análise de dados e automação: traduzir um fluxo real de trabalho em requisitos, estruturas de dados e etapas de implementação.

O conhecimento prévio do processo ajuda a identificar funcionalidades necessárias antes da programação. O protótipo, por sua vez, permite praticar tecnologias atuais enquanto o escopo é desenvolvido com cautela e validação.

Privacidade e propriedade intelectual

Este case foi reescrito para fins demonstrativos, sem citar a empresa de origem do processo, expor clientes, incorporar dados ou publicar materiais corporativos. O fluxograma é uma representação criada para o portfólio e não uma captura de um sistema da empresa.
